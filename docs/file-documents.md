# File document registration

`POST /api/profiles/{id}/documents/files` accepts multipart fields `expected_revision`, `kind`, and `file`, with the same authenticated session, CSRF, revision, ownership, idempotency, and combined profile capacity rules as text registration. Accepted extensions are TXT, DOCX, and PDF, with matching MIME and file signatures; generic or absent MIME is accepted only with a matching format. Maximum original size is 5 MiB, extracted text is limited to 100,000 UTF-8 bytes, and PDFs to 50 pages. Limits reject rather than truncate. The current default is five combined text and file documents.

202 returns owner-visible document metadata only; raw bytes and chunks are excluded from the response. Original bytes and their exact SHA-256 are stored privately; extracted text and per-paragraph/page character locators are private, with a separate hash per chunk. Successful extraction remains `queued` with a null job. Unsupported formats or mismatched signatures return 415 before persistence. Recognized but unreadable, encrypted, unsupported-content, image-containing, or scanned documents return `failed` with a sanitized `extraction_failed` code; originals are retained privately and no content is logged. There is no OCR or semantic analysis. To avoid silently omitting content, this slice rejects DOCX with drawings, text-bearing headers/footers, notes, tracked deletions, fields, or other unsupported objects, and PDFs with AcroForms, widget annotations, images, or Form XObjects. Unsupported documents can be converted to plain text before upload.

Parsing occurs in a child with a CPU limit and ten-second timeout. Linux applies a 512 MiB address-space hard limit; on macOS, which does not support that limit, the parent samples RSS and kills the child above 512 MiB. Sampling cannot guarantee a hard peak memory ceiling. The parent also monitors RSS on Linux, bounds concurrent children per process to two, and fails closed if monitoring is unavailable. DOCX archive size, expansion, paths, XML declarations and entities are checked; PDF decoded content is bounded inside the monitored child. ZIP and PDF parsing failure details are never exposed.

## Reproduce

Apply migration 0010 to a dedicated configured test database. From `backend`, run `L0_DATABASE_TESTS=1 .venv/bin/python -m unittest discover -s tests -p 'test_*documents.py'`. The tests use synthetic inputs and cover text and file persistence, replay, private data, DOCX parsing and hostile archives, PDF text/blank pages, limits, and child-process cleanup. After authenticating, POST a synthetic UTF-8 `.txt` file with the three multipart fields above and the CSRF header; expect 202, `source_type: file`, `status: queued`, `job_id: null`, then GET the returned document as the owner. OCR, model processing, GPU execution, URL extraction, retry, and deletion are not part of this slice.

## Recorded verification (2026-11-01)

Verification uses synthetic documents and a dedicated local PostgreSQL 16.14 / pgvector 0.6.0 database with migration 0010, Python 3.14.6, Node 26.5.0, pypdf 6.21.4, python-multipart 0.0.33, and psutil 7.2.2. The existing shared Python environment and GPU services were not modified.

- Focused document suite: 50 tests passed, including existing text/profile cases. Tests cover hostile DOCX XML, unsupported content, PDF inline images, atomic rollback, ownership, limits, and subprocess timeout/RSS termination and reaping. Resource tests simulate threshold breaches; they do not establish a strict macOS peak memory bound.
- Real HTTP smoke with a synthetic authenticated user: TXT, DOCX, and text PDF each returned 202 on registration and replay, then 200 on owner GET, with original SHA-256 preserved. An encrypted PDF returned 202 with `failed/extraction_failed`; a mismatched PDF signature returned 415. Profile revision reached 4 with four stored documents and no review token.
- Latest-main integration checks: web 276 passed; backend 295 run with one optional skip; launcher 22 passed; catalog unit 18 passed. Catalog integration: 10 passed; production TypeScript/Vite build passed. `./check` exited 0 against main commit `7828d59`.
- Browser file-upload E2E, OCR, semantic extraction, and GPU execution were not run in this slice. Successful parsing remains queued until the subsequent analysis integration; it is not evidence of complete issue #18 acceptance.

The HTTP fixtures were a Korean UTF-8 TXT with CRLF, a DOCX paragraph with tab/newline, and a single-page synthetic text PDF. Local evidence is retained under `.outline/file18-verification/` (`http-result.json`, `http_smoke.py`, synthetic fixtures, and `full-check.log`); these machine-specific artifacts are not required by the portable unit tests above.
