## 진행 순서와 의존성

1. P0 준비와 T08 CI는 병렬로 시작합니다. P0 전체 완료를 기다려야만 모든 구현을 시작하는 것은 아닙니다.
2. 계약 확정 후 A 화면, B 인증/프로필, C 질문 생성, D 원천 적재를 병렬 진행합니다. 목 개발은 가능하지만 실제 통합 완료로 닫지 않습니다.
3. P2A의 선택 질문과 P2B 카탈로그가 준비되면 T20의 **자료 없는 실제 추천 경로**부터 연결합니다.
4. D의 적재/검색 초기 작업 뒤 파일/OCR/링크 추출로 이동합니다. 같은 D에게 두 트랙의 전일 작업을 동시에 배정하지 않습니다. A/B는 상세·비교·저장, C는 실제 추천 품질을 병행합니다.
5. T14 자료 확인이 준비되면 T20 자료 포함 경로를 연결하고 P4에서 전체 검증합니다. 파일·링크를 최종 범위에서 제외하는 것이 아닙니다.

3명이면 A=웹, B=API·DB·자료, C=AI·데이터로 묶되 데이터 최소 적재 후 AI 추천으로 넘어가고 인프라는 시간을 나눠 담당합니다. 마감·투입시간이 없으므로 날짜나 완료 예상일은 만들어 넣지 않습니다.

## 충돌 방지와 병합

- 사용자 시나리오 하나에 이슈 하나. 영역별 `<종류>/<영역>/<이슈번호>-<작업>` 브랜치와 작은 PR. 중간 PR `Refs`, 실제 전체 완료 확인 후 마지막 PR만 `Closes`.
- 공용 계약은 B가 취합하고 영향 영역이 검토. YAML/JSON/TS/샘플 동시 변경.
- migration은 각 영역 작성, B가 down_revision·병합 순서 조정. 같은 head에서 충돌하는 revision을 조정 없이 합치지 않음.
- main.py=B, App/공통 스타일=A, compose/scripts/workflows=D. 겹치는 파일은 담당자와 범위를 맞춘 뒤 수정.
- xifoxy-ru·zxcv718 중 작성자가 아닌 리뷰어에게 요청. 사람 1명 이상 승인, Conventional Commit 제목, Squash and merge. 자동 승인·자동 배포 없음.
