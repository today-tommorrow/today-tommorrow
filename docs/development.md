# 개발 가이드

웹·API·DB 기반과 실제 DB health 확인을 구현했다. 업무 기능·샘플 모드·GPU·Nginx 배포는 아직 없으며 아래 관련 기준은 후속 구현에 적용한다. 설치와 공통 진입 절차는 [README](../README.md), 작업·리뷰 책임은 [팀 가이드](../AGENTS.md)를 따른다. 새 라이브러리와 큰 구조 변경은 관련 담당자와 먼저 합의한다.

## 웹: 화면 흐름과 상태

Vite + React + TypeScript의 SPA로 구현하고 TypeScript `strict`를 사용한다. 사용자 기능 단위로 화면·요청·상태를 가까이 두되 기존 구조에 맞춰 책임별로 나눈다. 폴더를 미리 늘리거나 범용 계층을 만들지 않는다.

컴포넌트 안에서만 쓰는 입력·열림 상태는 로컬에 둔다. 공유가 필요한 가장 가까운 부모로 올리고, 서버 응답은 API가 원본임을 유지한다. 필터처럼 링크로 공유할 상태는 URL 사용을 검토한다. 같은 데이터를 여러 저장소에 복사하거나 전역 상태 라이브러리를 기본으로 추가하지 않는다. 요청에는 로딩·빈 결과·오류·재시도 흐름을 명시한다.

Tailwind의 기본 간격·글자 크기·색상 척도를 우선 사용한다. 반복되는 버튼·입력·결과 표시만 컴포넌트로 묶고 같은 동작과 접근성 표시를 재사용한다. 임의 픽셀값·색상과 일회성 변형을 늘리지 않는다.

## 요청 경로와 정적 배포

브라우저는 같은 출처의 상대 경로 `/api/...`로 요청한다. 개발 시 Vite 프록시, 배포 시 Nginx가 `/api` 경로를 **제거하지 않고** FastAPI에 전달하고, 백엔드 라우트도 `/api` 접두사를 포함한다. 개발 대상은 루트 `.env`의 `API_TARGET`, 웹 포트는 `WEB_PORT`로 설정한다. 개발·배포가 서로 다른 경로 계약을 만들지 않게 같은 샘플로 확인한다.

웹 빌드 산출물 `dist`를 Nginx가 정적으로 제공하도록 구성한다. SPA 화면 경로의 직접 접근·새로고침에는 `index.html` fallback을 적용한다. `/api`와 정적 자산 요청은 이 fallback에서 제외한다. 존재하지 않는 API는 API의 404를 유지하고, 없는 JS·CSS·이미지 등 자산은 404를 반환해야 한다. 배포 검증에서 화면 새로고침, 정상 API, 없는 API, 없는 자산을 각각 확인한다. Vite 개발 프록시만 구현했으며 Nginx 호스팅은 아직 없다.

GPU 서버는 백엔드만 호출한다. 브라우저에 GPU 주소·인증 토큰을 전달하지 않는다. `VITE_` 환경변수는 빌드 결과에 노출되는 공개값이다. 서버 비밀은 백엔드 환경으로 주입하고 응답·로그에 노출하지 않는다. GPU가 없어도 로컬 샘플 모드로 화면·API 연동을 개발할 수 있게 하되 실제 추론과 구분한다.

## API: 계약과 읽기 쉬운 이름

FastAPI 라우트는 HTTP 입력·응답을 다루고, 업무 로직은 서비스 함수로 분리한다. 요청·응답을 Pydantic 모델로 정의하고 타입·필수값·범위를 검증한다. OpenAPI와 실제 응답이 같도록 정상·빈 결과·입력 오류 예시를 함께 검토한다. API 필드와 Python 변수는 뜻이 드러나는 `snake_case`, 모델 클래스는 `PascalCase`, React 컴포넌트는 `PascalCase`, TypeScript 함수·변수는 `camelCase`를 기본으로 한다. 필드명은 웹에서 임의로 번역하지 말고 계약을 따른다.

아래 추천 예시는 **설명을 위한 제안**이며 구현된 엔드포인트나 확정 계약이 아니다. 실제 시나리오 이슈에서 입력, 점수 의미·범위, 상태 코드와 오류 형식을 합의한 뒤 Pydantic/OpenAPI와 공통 샘플에 반영한다. README의 이미지 판정 예시와도 별개의 예시다.

| 경우 | 예시 요청 | 예시 응답 |
| --- | --- | --- |
| 정상 | `POST /api/recommendations` · `{"query":"산책"}` | `200 {"items":[{"id":"sample-1","title":"공원 산책","score":0.9}]}` |
| 빈 결과 | 같은 경로 · `{"query":"없는 조건"}` | `200 {"items":[]}` |
| 입력 오류 | 같은 경로 · `{"query":""}` | `422 {"detail":[{"loc":["body","query"],"msg":"검색어가 필요합니다","type":"value_error"}]}` |

웹은 빈 목록을 오류와 구분한다. 오류 문구만으로 분기하지 않고 합의한 상태 코드·필드를 사용한다. 백엔드 또는 GPU의 장애 응답은 내부 주소·토큰·스택을 숨기고 재시도 가능 여부를 전달하도록 별도 계약을 정한다. 예시 데이터는 합성값이다.

## DB: 세션과 변경 이력

개발 DB는 Compose의 PostgreSQL을 사용하고 ORM은 SQLAlchemy 2.x를 기준으로 구현한다. SQLAlchemy 세션은 요청 또는 작업 단위로 열고 반드시 닫는다. 전역 세션을 공유하지 않는다. 트랜잭션은 하나의 업무 변경 단위로 묶고 성공 시 커밋, 실패 시 롤백한다. 세션 종료와 트랜잭션 책임을 명확히 하고 보조 함수마다 임의로 커밋하지 않는다. 느린 GPU 호출을 기다리는 동안 불필요한 DB 트랜잭션을 열어 두지 않는다.

스키마 변경은 SQLAlchemy 모델과 Alembic 마이그레이션을 함께 제출한다. 자동 생성된 마이그레이션도 사람이 검토하고 기존 데이터·호환성에 미치는 영향을 적는다. 공유된 마이그레이션 이력을 고쳐 덮지 않는다. 개발 DB가 연결 가능한 뒤 적용하고 저장·재조회를 확인한다. 복구 방법은 변경 특성에 맞춰 설명하며 데이터 삭제나 무조건적인 downgrade를 기본 해결책으로 쓰지 않는다.

## 의존성과 검증

npm의 `package-lock.json`과 uv의 `uv.lock`을 저장소에 포함하고 팀이 같은 도구 버전·잠금 파일로 설치한다. 의존성 변경 PR에는 이유와 잠금 파일 변경을 함께 담는다. 웹 명세·잠금 파일은 `web`, API 명세·잠금 파일은 `backend`에 있다. 실행 명령은 README를 따른다.

구현할 공통 check에는 TypeScript 검사, ESLint·Prettier 웹 검사, Ruff Python 검사, 필요한 동작 테스트, 웹 빌드를 포함한다. 현재 TypeScript 검사와 웹 빌드만 제공하며 ESLint·Prettier·Ruff·공통 check는 아직 없다. PR에는 실행한 검사와 결과, 미실행 항목을 남긴다. PR에서 실제 실행한 환경만 검증했다고 기록하고 다른 Mac의 온보딩을 완료했다고 표시하지 않는다. 실제 모델·GPU 검증은 이슈 완료 조건에 따라 실행하고, 목·CPU·GPU 또는 해당 없음과 이유를 구분한다.
